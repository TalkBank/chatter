**Status:** Current
**Last updated:** 2026-09-03 18:06 EDT

## Description

A quotation “...” contains another quotation, at any depth and
through any container (a retrace group, a phonological group, a sign group,
an annotated quotation).

## Expected Behavior

Validation descends both sides of the relation, the enclosing quotation and
the enclosed one, through every container, and reports E372 once per
nesting. Two quotations side by side, or a quotation inside a container
that is not itself inside a quotation, are not reported.

**Trigger**: See examples above

## CHAT Rule

The CHAT manual introduces the quotation marks “ and ” for quoted
material but states no nesting rule; chatter's rule is structural: a
quotation is a container, and a container of the same kind inside it has no
CHAT meaning.

## Notes

Detected at ANY depth, through every container, and the rule has to descend on
BOTH sides of the relation: to the quotation that encloses, and to the one it
encloses.

Until 2026-08-07 the INNER predicate recursed into annotated groups only, so a
quotation inside a retrace, a phonological group, a sign group, or another
quotation was invisible: examples 2 and 3 reported nothing while example 1
reported E372.

Examples 4 and 5 are the same defect once more, and they survived that fix.
A quotation has TWO spellings in the model, with and without its own scoped
annotations, and each half of this rule named only the first. So an annotation
anywhere on either quotation hid the nesting completely, on the default backend
only:

- example 4, annotated on the OUTER quotation: example 1 with `[//]`, `[/]`,
  `[*]` or `[% note]` appended validated CLEAN, while example 1 without it
  reported E372;
- example 5, annotated on the INNER quotation: `“a “b” [% note] c”` validated
  CLEAN. `[//]` there did NOT leak, because a retrace marker lowers to a
  retrace, which the predicate already descended through. That is why one
  spelling of the same construct was caught and the other was not.

In both cases the re2c backend still reported E372 on the identical bytes, so
the two parsers disagreed about a validity rule.
