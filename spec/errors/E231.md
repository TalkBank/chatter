## Description

A word's shortening markers, `(` `)` around an omitted syllable/segment (e.g.
`(be)cause` for an elided "be"), must nest and balance like ordinary
parentheses: every `)` must be preceded by a matching unclosed `(`, and every
`(` must eventually be closed. The check is stack-based (implemented in
`crates/talkbank-model/src/validation/word/structure.rs::check_shortening_balance`),
not a bare count, so it also catches a `)` appearing before any `(` (reported
immediately, at the point of the stray close) in addition to a trailing
unclosed `(` (reported once, after the whole word is scanned).

**How an imbalance ever reaches this rule.** The grammar has no free-standing
`(` or `)` inside a word: parentheses exist there only as `shortening`, which
is `'(' word_segment ')'` and so is balanced by construction, and
`word_segment` forbids both characters outright. An unbalanced run in a word's
raw text is therefore always the residue of parser recovery, which is exactly
why the check reads `Word::raw_text` rather than the cleaned content: the
residue has to survive in order to be judged. Which recovery tree-sitter
chooses then decides whether the rule runs at all, and the two examples are
the two outcomes.

## Expected Behavior

For an input where the parser DOES build a `Word` value whose raw text
contains an unbalanced parenthesis run (rather than abandoning the word
entirely), model validation reports E231 at the point of the imbalance: an
early `)` is flagged immediately, a trailing unclosed `(` is flagged once
after the scan. Example 2 is that input, and the parse-stage diagnostic that
accompanies it (E342, the inserted `)`) is not incidental noise; see the
Notes.

## CHAT Rule

<https://talkbank.org/0info/manuals/CHAT.html#Word> documents `(text)` as the
shortening/omission marker; it must be a balanced, nestable pair around the
omitted material.

## Notes

- **E231 cannot fire alone, by construction.** Every input that reaches it
  also reports the recovery that let it through: E342 when tree-sitter
  inserts the missing `)` (example 2), and E316 when an ERROR node lands
  inside the word's own span, as in `he((l)lo .` and `he(l(o) .`, both of
  which report E316 and E231 together. A future example carrying only E231
  would mean the grammar had started admitting a bare parenthesis in a word,
  which would be the defect, not the improvement.
- **The stray-close branch has no example yet.** The `depth < 0` arm, a `)`
  before any `(`, is implemented and unreached. Probing on 2026-09-07 over
  `dog) .`, `do)g .`, `be)cause.`, `he(l))lo .`, `he(l))o.`, `(be))cause.`
  and `(be)cause).` found the surplus `)` landing OUTSIDE the word node every
  time: E231 fired on none of them, and the report was E316, joined by E209 on
  `(be))cause.`, whose word is left with no spoken content. That is evidence,
  not proof: the open question is whether any recovery puts a surplus `)`
  inside a `standalone_word` byte span, and a shape that does would
  demonstrate the second half of this rule.
- Example 1's `subsumed_by` claim is kept rather than replaced. It is still
  true, and it now earns its place as the contrast that names which recovery
  the parser picks and when, which is the fact a reader of this rule needs.
