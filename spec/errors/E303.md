## Description

A header line's colon is followed by something other than a single TAB: a
space, nothing at all, or the value run straight on. CHAT separates a header
name from its value with exactly one TAB, and a header that does not is not a
header the grammar can read.

## Expected Behavior

The multiword-header pair changes only the TAB after `@Recording Quality:`.
The control is clean and byte-exact. The deletion leaves a generated MISSING
tab in `header_sep`, so the structural recovery backstop reports E303 rather
than generic E342. Its recovered serialization diverges; the inserted separator
does not make the authored file valid. Other missing tokens retain their own
recovery diagnoses.
Deleting the colon while retaining the TAB instead produces ERROR recovery and
E316, not E303. That is a separate specificity gap, not a missing-TAB witness.
CHECK reports 132/17 on this mutation: its tab check rejects a noninitial TAB
not preceded by a colon, and its colon check fails to match a declared tier.
Those messages do not imply that the author's intended header name changed.

The `@Tape Location` pair exercises a different recovery shape: deleting its
TAB produces a whole ERROR header rather than a typed MISSING-tab slot. E303
still names the same separator defect, including the space inside the header
name. The control is clean and byte-exact; the mutation's serialization
diverges. CHECK 21-Sep-2026 accepts this control and reports error 3 for the
mutation through the same colon-check logic described below.

CHECK 21-Sep-2026 accepts the control and reports error 3 for the deletion.
In `check.cpp`, `check_Colon` advances past the colon and reports 3 when the
following character is not whitespace (1752–1759). That supports the shared
missing-separator diagnosis; CHECK's separate treatment of spaces and empty
header values does not define Chatter's entire separator policy.

Tree-sitter recovery leaves the line as an ERROR node; the parser recognizes
the header shape (`@`, a name of letters and spaces, a colon) and reports E303
over the line, saying what followed the colon ("A space", "Nothing", or the
character found). The rest of the file parses normally. A header whose colon
is followed by one TAB is not this rule's business, whatever else may be
wrong with its value.

**Trigger**: See examples above

## CHAT Rule

The CHAT manual's "File Headers" section defines every header as `@Name:`
followed by a tab and the value:
<https://talkbank.org/0info/manuals/CHAT.html#File_Headers>. CLAN CHECK
reports the same defect as its error 8 ("Expected @, %, *, TAB").

## Notes

- The registry variant is the historical `SyntaxError`; what it means today
  is exactly this rule, decided in
  `error_analysis/file.rs` from a typed split of the header line at its colon
  (`HeaderColon`, `AfterHeaderColon`), never from a header-name allowlist.
- Headers without a colon (`@Begin`, `@End`, `@UTF8`) cannot trigger it.
- A main tier with a space after its colon (`*CHI: hello .`) is a different
  shape and reports E316; a dependent tier with one (`%com: note`) reports
  E602.
