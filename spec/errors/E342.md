## Description

Tree-sitter recovered the parse by inserting a MISSING placeholder for a
required element that the source does not contain: an annotation after an
angle-bracket group, a word segment inside a replacement. Recovery is not
validity, so the placeholder is reported.

## Expected Behavior

The parser reports E342 at the recovery position. The angle-bracket case
below is the canonical one; the replacement case (`helo [: 0] world`) is
malformed at both stages and E390 names the more specific defect beside
it. A source with the required element present is not reported.

**Trigger**: See examples above

## CHAT Rule

Scoped symbols follow the group they scope over (https://talkbank.org/0info/manuals/CHAT.html#Scoped_Symbols);
a replacement carries replacing text (https://talkbank.org/0info/manuals/CHAT.html#Replacement_Scope).

## Notes

- Until 2026-09-03 this code had two spec files; the machine-written one
  also carried three examples subsumed by E760 and E316 (a `%mor` item with
  an empty part of speech or stem, a `%gra` item with no relation), which
  E382, E702 and E710 now document; they are dropped here.

### The bare angle-bracket group

An angle-bracket group `<...>` on the main tier must be followed by an
annotation (a retrace marker such as `[//]`, a scope code such as `[?]`,
an explanation `[= ...]`, etc.). A bare `<...>` group with nothing after
it is malformed CHAT. CLAN's `check` reports it as
`expected [ ]; < > should be followed by [ ]`.

The tree-sitter grammar's `group_with_annotations` rule requires at least
one annotation after the group, so on a bare group tree-sitter recovers by
inserting a synthetic `MISSING retrace_complete` node (visible in
`tree-sitter parse` as `(MISSING retrace_complete [r,c]-[r,c])`) and
continues. **Recovery is not validity**: the document did not conform to
the grammar, so the parser surfaces E342 (MissingRequiredElement) on the
recovery node while still producing a usable AST for downstream repair and
the LSP. The recovered model shape is the bare `Group` that was written,
with no marker: the annotation decoder skips a MISSING node rather than
reading its kind (until 2026-09-09 it read the kind and built a
`Retrace { kind: Full, is_group: true }` nobody wrote, on which validation
then reported E757 and E370, and the roundtrip diverged). A bare group is
a shape valid CHAT never produces, which is why the invalidity is detected
at the parser (recovery-node) level rather than from the AST.

This pattern is a data error. The fix is in the corpus, not the parser:
add the intended annotation after the group (e.g., `<I don't> [//]`), or
remove the angle brackets if no scope was meant.

#### Expected behavior

The parser must emit E342 on the recovery position (the point where the
required annotation was expected). The AST is still produced (the group
stays a bare group, and serializes back to the bytes that were written) so
downstream tooling can repair the file;
the diagnostic carries the file path, line, and column so a corpus
maintainer can locate and correct the data.

#### Remediation guidance (for data maintainers)

When E342 fires on this pattern, add the annotation the group needs (most
often a retrace marker `[//]`), or drop the `<...>` if no grouping was
intended. A bare `<...>` group is never valid CHAT.
