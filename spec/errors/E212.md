## Description

E212 reports malformed word fragments and invalid CA-omission model shapes.
It is reachable from complete CHAT input: in CA mode, an explicit category
prefix prevents standalone-shortening normalization. `0(the)` retains the
omission category and one `Shortening` node, so validation reports E212 and
E209 (no spoken content). The legal neighbors are `(the)`, which normalizes to
a CA omission, and `0the`, which retains ordinary text content.

The historical `hello world .` example is legal and stays as a control. Its
embedded comment describes the old fixture's provenance, not a parser failure.

## Expected Behavior

The diagnostic has three distinct entry points:

- **Isolated-word API:** `single_item/parse_word.rs` rejects empty input, input
  that does not parse as one standalone word, and failed word conversion.
  Existing snapshot regressions include empty word input, an unclosed
  shortening and a missing form type. These are fragment API tests; wrapping
  the same text in a CHAT file can produce different diagnostics.
- **Main-tier fragment API:** `api/parser_api.rs` reports E212 when CA omission
  shorthand requires file context that the caller has not supplied. A full
  file with `@Options: CA` has that context, so this fragment rejection does
  not establish a whole-file violation.
- **Model validation:** `model/content/word/word_validate.rs` reports E212 for
  a `CAOmission` outside CA mode, a CA omission without spoken text or with
  shortening/compound content, and a single shortening element that remains
  unnormalized in CA mode. Programmatic model construction can reach these
  checks. Both file parsers normalize eligible CA omissions before validation;
  explicit category prefixes are deliberately excluded from that rewrite.

In standard CHAT, a standalone `(the)` is covered by E209 (no spoken content).
It is not a supported E212 example merely because it consists of a shortening.

## Reachability audit

The whole-file example above closes the former coverage gap without treating
an API-only rejection as a file-level violation. Regenerate observations with
`just regen`: the prefixed standalone shortening reports E209 and E212; both
legal controls omit E212. The shared normalizer's category guard is the reason
this case survives, not a missing parser call.

This does not claim that every programmatically constructible invalid
`CAOmission` can arise from CHAT. Those model checks still defend the editable
model boundary independently.

## CHAT Rule

Whole-file interpretation of CA omission shorthand depends on the file's CA
options. Fragment API context requirements and model representation invariants
are separate from the validity of the historical full-file example here.
