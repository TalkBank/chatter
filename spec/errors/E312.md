## Description

Opening bracket `[` on the main tier has no matching closing bracket `]`.

## Expected Behavior

The parser reports E312 when an ERROR node's text opens with `[` and holds
no `]` (`UnclosedDelimiter` in `tree_parsing/helpers.rs`, read by the
generic ERROR analyzer and by the main-tier classifier alike). Whether a
given unclosed bracket produces such a node depends on what tree-sitter's
recovery leaves behind, which varies by what follows the bracket: the
second example reaches E312; the first is E375, because its ERROR node
holds more than the bracket; a stray `[` inside a construct with more
material after it is E316 at that byte. No general rule is known for when
recovery produces the E312 node.

## CHAT Rule

See CHAT manual on annotation brackets. All bracket notation must be
properly opened and closed: `[= comment]`, `[: replacement]`, etc.

## Notes

- The pattern is `UnclosedDelimiter::in_error_text` in
  `tree_parsing/helpers.rs`, over the ERROR node's own text; since
  2026-09-08 it has one owner and is applied on the tier body and inside
  every bracketed construct.
- Tree-sitter's recovery rarely leaves an ERROR node holding only the
  unclosed bracket; it usually splits the parse elsewhere, and those forms
  produce E375, E304 or E316 instead. The second example is the measured
  exception.
