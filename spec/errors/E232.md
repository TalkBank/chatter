## Description

Compound marker (`+`) cannot be at the start of a word. Valid compounds have
the form `left+right`, where both parts carry spoken material.

## Expected Behavior

For an input where the parser DOES build a `Word` whose first content element
is a compound marker, model validation reports E232 on that word. The
canonical tree-sitter parser never builds such a word from CHAT text, so the
example above does not reach the rule and claims only what it observes: E316,
the generic unparsable-content report for the ERROR node the `+` lands in.
The Notes carry the mechanism and the search behind that claim.

## CHAT Rule

<https://talkbank.org/0info/manuals/CHAT.html#Compounds> documents the
`left+right` compound-word form; `+` is a joining marker between two parts and
is not valid as a word-initial character.

## Notes

- **Why no CHAT input reaches the check.** The only emit site is
  `check_compound_markers` in
  `crates/talkbank-model/src/validation/word/structure.rs`, and its condition
  is that `word.content().first()` is a `CompoundMarker`. A
  `WordContent::CompoundMarker` is constructed in exactly one place, from an
  anonymous `"+"` child of a `word_body` node. The grammar puts `'+'` in
  `_word_marker`, and `word_body` admits `_word_marker` only in the TRAILING
  `repeat(...)` of both its alternatives: the leading position is
  `word_segment | shortening | stress_marker`, or a run of
  `overlap_point | ca_element | ca_delimiter | underline_begin |
  syllable_pause` which must itself be followed by one of those three. `+` is
  additionally in `WORD_SEGMENT_FORBIDDEN_COMMON`, so no `word_segment` can
  carry one. A word-initial `+` therefore has no grammar position at all, is
  skipped into an ERROR node, and becomes E316.

- **The silent-drop route is closed as well.** `build_word_contents` pushes
  nothing for a `word_segment` or `shortening` whose text is empty, and
  nothing for a `ca_element` or `ca_delimiter` whose character it does not
  map. A dropped leading child would expose the `+` as first. Neither drop is
  reachable: the token regexes make both segment kinds non-empty, and the
  grammar's symbol sets (`WORD_ATTACHED_SYMBOLS`, ten characters, and
  `PAIRED_STRETCH_SYMBOLS`, fifteen) match the Rust match arms exactly, so
  both `None` fallthroughs are dead code.

- **E231's recovery trick does not transfer, and that was tested rather than
  assumed.** E231 is demonstrated by `be(cause.`, where tree-sitter completes
  the word by INSERTING a missing `)`. The equivalent here would be an
  inserted zero-width `word_segment` ahead of the `+`, which `WordText::new`
  would reject and drop. Probing on 2026-09-07 over 33 shapes found
  tree-sitter never doing it: `+hello .`, `+hello.`, `hi +hello .`,
  `<+hello> .`, `dog [: +cat] .`, `0+hello .`, `()+cream .`, `()+cream.`,
  `(+cream.`, `^+banana .`, `+hello@c .`, `+hello$n .`, `hello@c+world .`,
  `~+hello .` and a `%wor` tier carrying `+hello` all report E316. The
  sharpest of them is `⌈+hello⌉ .`, where the grammar REQUIRES a
  `word_segment` immediately after the leading overlap marker, which is
  structurally the same hole `be(cause.` exploits; it too reports E316.

- **The nearest legal neighbour, and a shape worth noticing.** `ˈ+hello .`
  parses with NO diagnostics at all: its content is
  `[StressMarker, CompoundMarker, Text]`, and the `+` still has no left
  segment. E232 asks whether the marker is FIRST, not whether spoken material
  precedes it, so any leading marker hides the same defect. The sibling rules
  in this same function are written the other way round (E245, E246 and E252
  all ask `spoken.follows` or `spoken.precedes`), which makes this an
  inconsistency rather than a deliberate narrowing. Recorded here, not fixed
  here.

- **`check_compound_markers` itself is live.** `ice+ .` reports E233 from the
  trailing branch of the same function, and `ice++cream .` reports E233 from
  the parser's `misplaced_linker_error` carve-out. It is the LEADING branch
  alone that no input reaches.

- **The registry status is right; the demonstration is what is missing.**
  `status = "implemented"` rather than `unreachable_from_chat`, because the
  rule does fire on CHAT through the re2c backend. Closing the gap would take
  a code change, not a spec change: either the grammar admits a word-initial
  `+` so the model can name it (the strict-plus-catch-all move that gave
  `^banana` its E252), or a parser-level classifier branch beside the E233
  carve-out in `misplaced_linker_error`.
